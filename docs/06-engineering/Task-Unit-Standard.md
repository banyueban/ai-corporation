# 解耦任务单元规范

| 属性     | 内容                                                     |
| -------- | -------------------------------------------------------- |
| 文档版本 | 1.0                                                      |
| 适用范围 | AI Corporation Desktop 的实现、修复和 Milestone 交付任务 |
| 最近更新 | 2026-07-29                                               |

## 1. 目的

任务单元是项目中最小的、可以独立进入实施、独立失败、独立验收和独立关闭的工作封装。它解决以下问题：

- 防止把 Milestone、功能、工程动作和后续工作混在同一状态列表；
- 防止用不对应目标交付物的代理信号代替验收；
- 防止未声明的前置条件在执行中才暴露；
- 防止多个任务通过共享文件、共享数据或共享测试环境互相污染；
- 防止一个任务通过后自动抬高其他任务或整个 Milestone 的完成状态。

任务单元不是新的验收层级。它承载 [统一验收标准](Acceptance-Standard.md)中的 L1 变更或一个边界清晰的 L2 功能切片；低层任务单元通过，不自动代表完整 L2、L3 或 L4 通过。

## 2. 解耦判定

一个任务单元只有同时满足以下条件，才可称为边界清晰且可独立验收：

1. **单一主要结果**：只产生一个可观察的用户结果或系统能力；
2. **范围封闭**：明确列出包含范围和非范围；
3. **依赖显式**：输入、前置条件、基线提交和上游接口均可定位；
4. **交付物专属**：每项代码、Schema、迁移、文档或 UI 产物都有明确归属；
5. **验收直接**：每条断言都对应目标层级的真实交付物，不使用替代信号；
6. **测试隔离**：测试数据、临时目录、端口、数据库和进程生命周期不依赖其他任务残留状态；
7. **失败局部化**：该单元失败时，只回退该单元状态，不修改无关任务的完成状态；
8. **干扰可控制**：共享文件和共享接口被列为冲突区，并规定串行修改或兼容策略；
9. **证据可追踪**：证据对应同一提交、平台和产物，旧证据不得冒充当前证据；
10. **可单独关闭**：不需要把“顺便完成”的工作包装进本单元才能通过。

解耦不等于完全没有依赖。协议、迁移、公共状态机、CI 和 `PROJECT_STATUS.md` 天然是共享资源；它们必须显式声明并串行集成。

## 3. 强制任务合同

进入实现前，任务单元必须在 `docs/06-engineering/task-units/` 下建立合同，并至少包含：

| 字段           | 要求                                             |
| -------------- | ------------------------------------------------ |
| 任务单元 ID    | `M<里程碑>-TU-<两位序号>`，例如 `M1-TU-01`       |
| 状态           | 未开始、就绪、进行中、部分完成、阻塞、失败或完成 |
| 所属 Milestone | 唯一 Milestone                                   |
| 主要结果       | 一句话描述可观察结果                             |
| 需求与设计引用 | 用户要求、PRD、架构、协议、UI 和安全来源         |
| 基线提交       | 开始实施时的 Git commit                          |
| 前置条件       | 仓库、权限、工具链、上游接口和数据               |
| 包含范围       | 本单元承诺交付的内容                             |
| 非范围         | 明确排除的相邻能力和后续任务                     |
| 依赖与接口     | 输入、输出、Schema、错误和兼容约束               |
| 交付物与所有权 | 预计修改的模块以及共享冲突区                     |
| 验收合同       | 正常、异常、安全、恢复和适用的平台断言           |
| 隔离方式       | fixture、临时目录、数据库、端口、进程和清理策略  |
| 证据计划       | 精确命令、报告、截图或 CI job                    |
| 完成规则       | 哪些条件满足后才能标记完成                       |

禁止使用“待实现时再定”“大致通过”或未分配责任的 `TBD` 作为就绪任务的合同内容。

任务合同的“需求与设计引用”必须直接链接 [MVP Plan](MVP-Plan.md) 中对应 Milestone；包含范围、非范围和完成规则必须说明本单元对该 Milestone 的贡献及剩余范围。任务不得引入所属 Milestone 未规定的产品能力。

## 4. 生命周期与门禁

```text
未开始 → 就绪 → 进行中
                   ├→ 部分完成
                   ├→ 阻塞
                   ├→ 失败
                   └→ 完成
```

合同审查、实施和验收是推动状态变化的阶段动作，不是额外状态。

### 4.1 就绪门禁

标记“就绪”前必须确认：

- 仓库和目标分支存在且具有所需权限；
- 基线提交已记录，工作区中的已有修改已识别；
- 需求、设计、非范围和验收断言无重大歧义；
- 上游接口已存在，或本单元已定义不改变生产语义的 mock/fake；
- 适用平台和无法本地验证的平台已明确；
- 交付物所有权及共享冲突区已明确；
- 所需命令、工具和外部凭据可用，或阻塞状态已登记。

前置条件不存在时，应执行已授权且可恢复的初始化动作；例如目标 GitHub 仓库不存在且用户已要求托管时，应创建仓库，而不是把“仓库不存在”当作未定义的终点。

### 4.2 实施门禁

- 只修改合同包含范围内的文件和接口；
- 新发现的相邻工作进入非范围或新的任务单元；
- 共享协议、迁移、状态机、安全策略和 CI 变更必须串行集成；
- 任务单元不得修改其他任务单元的完成状态；
- 合同发生实质变化时，先更新合同并重新检查边界。

### 4.3 验收门禁

每条验收断言必须形成：

```text
断言
→ 目标交付物
→ 验证环境
→ 验证动作
→ 可观察结果
→ 当前提交的证据
```

提交最终验收候选前，必须把合同中的每条断言展开为当前证据矩阵并逐项核对。包含多个状态、恢复机制、平台或产物形态的复合断言，必须展开为这些维度的笛卡尔子项；只覆盖其中一条路径不得勾选整条断言。矩阵中没有当前提交直接证据的子项保持未完成。

以下替代关系无效：

- 构建成功 ≠ 启动成功；
- 进程存活 ≠ 窗口可交互；
- 开发态运行 ≠ 最终打包产物运行；
- 单元测试通过 ≠ 用户旅程通过；
- mock 通过 ≠ 真实外部系统通过；
- 一个平台通过 ≠ 跨平台通过；
- 清理脚本失败 ≠ 功能必然失败，但二者必须分别记录，不能隐藏任一失败。

### 4.4 完成门禁

任务单元只有在以下条件全部满足后才可标记“完成”：

- 合同中的所有适用验收断言已通过；
- 证据对应当前提交和目标交付物；
- P0/P1 为 0，P2/P3 已登记；
- 测试没有依赖其他任务残留数据或进程；
- 共享接口的兼容检查和必要回归已通过；
- 文档、Schema、迁移与实现一致；
- `PROJECT_STATUS.md` 只更新本单元及其所属 Milestone 的真实状态。

## 5. 干扰控制

### 5.1 文件与接口

- 每个任务合同列出“专属修改区”和“共享冲突区”；
- 两个进行中的任务不得同时拥有同一迁移编号、协议版本或状态机定义；
- 共享文件由一个任务串行修改，其他任务通过已冻结接口工作；
- 若共享接口必须改变，下游任务暂停在“阻塞”或重新建立基线。

### 5.2 测试与运行环境

- 临时目录、数据库和用户配置使用任务 ID 或随机标识；
- 测试自行创建前置数据并清理，不依赖执行顺序；
- 端口动态分配或检查占用；
- 子进程必须等待退出，清理失败单独报告；
- 测试不得读取其他任务生成但未声明的构建缓存；
- 跨平台证据分别记录，不相互代替。
- fixture 路径验证器可以接受受控的任务单元 ID 格式，但不得硬编码为前一个任务 ID；自动测试必须同时证明当前任务、后续合法任务和非法前缀的接受/拒绝行为。
- 键盘/焦点、进程重启、持久化恢复和清理是独立环境变量，应分别形成断言；除非焦点恢复本身属于产品要求，不得把重启恢复是否通过绑定到 OS 是否把键盘焦点交给新进程。

### 5.3 状态与证据

- `PROJECT_STATUS.md` 只记录当前任务单元、当前 Milestone 和当前有效证据摘要；
- 任务单元完成只关闭自身，不自动关闭后续单元；
- Milestone 只有在其全部必需任务单元和 Milestone 级演示通过后关闭；
- 证据记录包含 commit、平台、产物、命令或 CI run/job；
- 验收报告必须同时考虑失败与成功证据；原始记录保存在测试产物、CI 和 Git 中，`PROJECT_STATUS.md` 不复制过程时间线。

## 6. 阶段复盘

每个 Milestone 关闭后、下一个 Milestone 首个实现任务开始前，必须完成一次阶段复盘：

1. 目标与实际交付；
2. 返工、阻塞和错误决策；
3. 直接原因与系统性根因；
4. 哪些控制有效、哪些缺失；
5. 可执行改进项及其落点；
6. 下一 Milestone 的任务单元如何应用这些改进。

复盘不是验收替代物，也不得修改已经发生的证据。项目不单独保存复盘历史文档；有效结论必须直接更新当前规范、自动检查、模板或下一任务合同，未落地的“经验”不算完成改进。原始过程由 Git、CI 和测试产物保存。

## 7. 自动检查

运行：

```text
pnpm check:task-units
```

检查至少覆盖：

- 文件名与任务单元 ID 一致；
- 强制元数据和章节存在；
- 状态使用受控词汇；
- “就绪”及后续状态不存在 `TBD`/“待定”；
- “完成”状态下验收清单不存在未完成项；
- 任务单元 ID 不重复。

自动检查只验证合同结构，不能代替合同内容审查或实际验收。
