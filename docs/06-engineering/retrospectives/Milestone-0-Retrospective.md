## 1. 目标与实际交付

Milestone 0 的目标是建立可重复构建的空应用。最终交付包括 pnpm/Cargo workspace、Electron Main/Preload/Renderer、Rust Sidecar health RPC、SQLite migration runner、安全基线、自动化检查、Windows/macOS 构建，以及两个平台最终打包应用的真实窗口与 Rust health E2E。

最终验收证据来自 GitHub Actions run `30415519753`：Windows x64 与 macOS Apple Silicon 均直接启动最终打包应用，窗口显示 `Native Core ready · v0.1.0`，随后上传对应 artifact。状态文档提交后的最新 HEAD 又由 run `30415888376` 完整回归通过。

## 2. 影响交付的问题

### 2.1 项目状态记录错位

现象：`PROJECT_STATUS.md` 的“尚未开始”章节曾包含“任何产品功能实现”之类不属于 Milestone 0 实施清单的条目。

影响：当前交付物与未来范围混在一起，完成标记失去明确语义，容易错误推动 Milestone 状态。

直接原因：状态文档只有自由文本，没有检查章节语义和 Milestone 边界。

系统性根因：没有先把 Milestone 拆成边界明确的任务单元，也没有规定每个状态条目必须归属唯一任务单元或 Milestone 交付物。

### 2.2 GitHub 仓库不存在时没有执行创建分支

现象：初始化流程发现远程仓库不存在后，没有立即把“创建仓库”作为已授权托管目标的恢复路径。

影响：Git 初始化和远程交付被无谓阻塞，需要用户手工补充本可预见的前置条件。

直接原因：只检查了仓库是否存在，没有在任务开始前定义“存在/不存在”两条处理路径。

系统性根因：缺少就绪门禁；仓库、权限、认证、工具链和恢复动作没有作为任务合同的前置条件逐项确认。

### 2.3 用进程存活代替最终应用可用

现象：最初只验证 Windows unpacked 进程存活数秒，并结合开发态 E2E 和安装包生成，错误推断打包应用已通过。

影响：最终打包应用的窗口、Renderer → IPC → Rust health 链路没有直接证据，Milestone 0 被过早标记完成。

直接原因：把构建、进程、开发态 E2E 和打包产物 E2E 当成可以相互替代的证据。

系统性根因：验收断言没有显式绑定目标交付物、运行环境、可观察结果和当前提交；存在为了尽快闭环而接受代理信号的确认偏差。

### 2.4 功能结果与测试清理结果耦合

现象：Windows CI 已观察到真实窗口和 `Native Core ready`，但临时 profile 清理发生 `EPERM`，使 job 失败。

影响：功能结果和测试基础设施结果难以区分，artifact 上传被阻断。

直接原因：子进程终止后没有等待完全退出，清理时仍可能占用 profile。

系统性根因：测试合同没有分别定义“功能断言”“生命周期/清理断言”和失败分类。

## 3. 哪些控制有效

- CI 双平台矩阵暴露了干净环境、换行符、构建依赖和 Windows 进程清理问题；
- 安全配置自动测试避免为绕过外层沙箱冲突而关闭应用自身 Chromium sandbox；
- 完成标记撤销后保留失败证据，没有用局部成功覆盖失败 job；
- 新增最终打包应用 E2E 后，窗口和 Rust health 成为直接、可重复证据；
- `pnpm check:status` 已能阻止 Milestone 0 在必需验收项未勾选时被关闭。

## 4. 改进项与落点

| 问题               | 改进                                           | 落点                              | 强制方式                            |
| ------------------ | ---------------------------------------------- | --------------------------------- | ----------------------------------- |
| 状态记录错位       | 所有实现任务归属唯一任务单元                   | `Task-Unit-Standard.md`、任务合同 | `check:task-units` + `check:status` |
| 前置条件缺失       | 增加就绪门禁和恢复分支                         | 任务合同“前置条件”                | 就绪前审查                          |
| 代理信号冒充验收   | 断言绑定产物、环境、动作、结果和 commit        | 验收标准、任务合同                | CI/人工证据审查                     |
| 测试互相污染       | 独立 fixture、临时目录、端口、数据库和进程清理 | 任务合同“隔离与干扰控制”          | 自动测试 + 清理检查                 |
| 完成状态外溢       | 单元通过不自动推动其他单元或 Milestone         | 任务单元规范                      | 状态结构检查                        |
| 经验未进入后续工作 | Milestone 关闭后强制复盘                       | 本文及 MVP 计划                   | 下个 Milestone 就绪门禁             |

## 5. 对 Milestone 1 的应用

Milestone 1 不作为一个整体直接开工。首个任务单元为 [M1-TU-01 Workspace 选择与路径边界](../task-units/M1-TU-01-workspace-boundary.md)：

- 只负责 Workspace 选择、授权元数据和 Rust canonical path 边界；
- 明确排除 Corporation CRUD、Goal Contract 和完整文件工具；
- 使用任务专属临时目录和数据库；
- 把工作区内路径、工作区外路径、路径穿越、符号链接/重解析点及权限变化分别列为验收断言；
- 该单元完成后仍不会把 Milestone 1 或相邻功能标记完成。

## 6. 复盘结论

Milestone 0 最终交付已通过，但过程暴露出任务边界、就绪检查和证据对应关系不足。问题不是单个命令失误，而是执行单元没有被正式建模。后续以解耦任务单元作为实施入口，并用结构检查、直接证据和阶段复盘形成闭环。
