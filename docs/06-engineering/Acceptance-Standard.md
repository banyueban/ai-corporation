# AI Corporation Desktop v0.1 统一验收标准

| 属性 | 内容 |
|---|---|
| 文档版本 | 1.0 |
| 适用范围 | AI Corporation Desktop v0.1 全部产品、设计与编码工作 |
| 文档地位 | 唯一验收入口 |
| 最近更新 | 2026-07-29 |

## 1. 目的

本文档统一 Definition of Done、功能验收、测试证据、缺陷门槛、安全门槛和发布门槛。

其他文档仍定义具体需求和技术约束，但验收工作必须从本文档进入。发生冲突时：

1. 安全硬限制优先；
2. 已确认的用户目标和 PRD 产品范围优先；
3. 本文档的完成与证据要求优先；
4. 模块详细设计与工程实现建议随后；
5. 无法消解的冲突必须停止相关交付并请求决策。

## 2. 验收层级

```text
L1 变更验收
  → 单个代码、文档、配置或迁移变更

L2 功能验收
  → 一个用户故事或模块能力

L3 Milestone 验收
  → MVP-Plan 中一个完整里程碑

L4 产品发布验收
  → AI Corporation Desktop v0.1 发布
```

低层通过不自动代表高层通过。

## 3. 项目级 Definition of Done

一个任务只有同时满足以下适用条件，才能标记为完成。

### 3.1 范围与需求

- [ ] 实现内容与用户要求和当前 Milestone 一致；
- [ ] PRD 中对应功能需求和非功能需求已建立映射；
- [ ] 未实现任何未经授权的重大范围扩张；
- [ ] 非目标没有被误实现为 v0.1 必需能力；
- [ ] 用户可见行为、失败行为和边界已明确。

### 3.2 设计一致性

- [ ] 遵循已接受的架构决策；
- [ ] 符合领域模型和状态不变量；
- [ ] IPC、RPC、Agent、Task、Artifact 和 Event 数据符合对应协议；
- [ ] TypeScript、Rust、SQLite 和 Electron 的职责边界没有被破坏；
- [ ] 设计发生变化时，相关文档与 Decision Record 已同步；
- [ ] 没有重复定义互相竞争的状态机、协议或策略规则。

### 3.3 实现质量

- [ ] TypeScript strict、Rust 编译和静态检查通过；
- [ ] 外部输入均经过运行时 Schema 验证；
- [ ] 错误、取消、超时和恢复路径已实现；
- [ ] 金额、Token、时间和 ID 使用约定的数据类型；
- [ ] 没有无理由的 `any`、`unwrap`、`expect` 或字符串匹配错误分支；
- [ ] 平台差异封装在适配层；
- [ ] 日志、错误和事件不泄露秘密或无必要敏感内容。

### 3.4 数据与迁移

- [ ] Schema 与领域模型一致；
- [ ] 新迁移不可变、可从受支持旧版本向前执行；
- [ ] 外键、唯一性、CHECK 和索引满足设计；
- [ ] 状态变化与领域事件在同一事务提交；
- [ ] Artifact 内容和数据库元数据保持完整；
- [ ] 备份、恢复或数据删除受影响时已补测试。

### 3.5 安全

- [ ] Renderer 没有 Node、密钥或任意文件权限；
- [ ] IPC/RPC 使用白名单与 Schema；
- [ ] 文件访问经过 canonical path 和工作区边界检查；
- [ ] Tool Call 经过 Policy Engine；
- [ ] 命令使用 executable 与参数数组，不使用任意 shell；
- [ ] 高风险或不可逆操作按策略审批；
- [ ] Prompt、Artifact、网页和模型输出均视为不可信内容；
- [ ] 取消与恢复不会重复已确认副作用。

### 3.6 文档和运行方式

- [ ] 代码、协议、Schema、迁移和文档一致；
- [ ] 新增配置有默认值和说明；
- [ ] 启动、测试、构建方式可执行；
- [ ] 已知限制明确记录；
- [ ] `PROJECT_STATUS.md` 已更新。

## 4. 功能验收

### 4.1 验收来源

每个功能必须形成下面的追踪链：

```text
用户目标
→ PRD FR/NFR/AC
→ 模块详细设计
→ 实现变更
→ 测试用例
→ 测试证据
```

无法关联到需求或设计的实现，必须说明其必要性；无法关联到测试证据的功能不得验收。

### 4.2 功能验收模板

每个功能至少记录：

| 字段 | 要求 |
|---|---|
| 功能名称 | 可被用户或上游模块识别 |
| 需求引用 | PRD FR/NFR/AC 编号或明确用户要求 |
| 设计引用 | 对应模块和协议文档 |
| 前置条件 | 环境、数据和权限 |
| 正常场景 | 预期输入、动作和结果 |
| 异常场景 | 错误、超时、拒绝和恢复 |
| 安全场景 | 越权、注入或副作用边界 |
| 跨平台范围 | Windows、macOS 或不适用原因 |
| 测试证据 | 命令、结果、报告或截图引用 |
| 已知限制 | 未覆盖范围及风险 |

### 4.3 产品级必过场景

发布前必须通过 [PRD](../01-product/PRD.md) 中：

- AC-01 文档任务闭环；
- AC-02 权限阻断；
- AC-03 崩溃恢复；
- AC-04 质量修订。

产品场景必须端到端执行，不能仅由单元测试替代。

## 5. 测试要求

详细测试范围以 [Testing-Strategy.md](Testing-Strategy.md) 为准。本节定义最低验收门槛。

### 5.1 变更对应测试

| 变更类型 | 最低要求 |
|---|---|
| 纯函数、评分、转换 | 单元测试 |
| 状态机、预算、Policy | 单元测试 + 非法路径测试 |
| Repository、SQLite、FTS | 组件测试 + 迁移/约束测试 |
| Provider Adapter | Mock HTTP 合同测试 + 错误归一化 |
| IPC/RPC | Schema、鉴权、非法调用和集成测试 |
| Tool/文件/进程 | 组件测试 + 安全攻击测试 + 取消测试 |
| Artifact/Change Set | 原子性、冲突、路径和恢复测试 |
| Agent/Task/Evaluation 闭环 | 集成测试 |
| 用户可见关键旅程 | Electron E2E |
| 跨平台能力 | Windows/macOS 对应测试 |

### 5.2 必须执行的工程检查

项目初始化完成后，正式命令以仓库脚本为准，但至少覆盖：

- format check；
- TypeScript lint；
- TypeScript typecheck；
- Rust fmt；
- Rust clippy；
- 单元测试；
- 集成测试；
- migration test；
- secret scan；
- Electron security test；
- 适用的 E2E；
- Windows/macOS build。

若项目尚未提供某项命令，它属于当前 Milestone 的缺口，不得把“没有脚本”记录为通过。

### 5.3 测试不得被跳过的情况

以下变更必须运行对应测试：

- 状态迁移；
- 数据库 Schema 或迁移；
- Policy 默认值；
- Tool、IPC、RPC；
- 路径或命令处理；
- 凭据与日志；
- 崩溃恢复；
- Provider 错误和回退；
- Artifact 提交。

## 6. 验收证据

### 6.1 可接受证据

- 执行过的精确命令和退出结果；
- 自动化测试报告；
- 构建产物及平台；
- 数据库 migration/foreign-key check；
- E2E 运行记录；
- 安全攻击用例结果；
- 可复现的人工验收步骤；
- Artifact、事件或诊断报告引用；
- 必要的 UI 截图或录屏。

### 6.2 不可接受证据

- “代码看起来正确”；
- “理论上可以运行”；
- 模型对自己实现的评分；
- 未实际执行的命令清单；
- 只有正常路径、没有错误和恢复路径；
- 与当前提交或工作区状态不对应的旧测试结果；
- 隐瞒失败测试或只展示局部成功输出。

### 6.3 无法执行测试

必须记录：

1. 未执行的测试；
2. 无法执行的具体原因；
3. 影响范围；
4. 当前剩余风险；
5. 谁、在什么环境、如何补验；
6. 在补验前任务属于“部分完成”还是“阻塞”。

## 7. 缺陷门槛

| 级别 | 定义 | 验收处理 |
|---|---|---|
| P0 | 未授权副作用、数据损坏、密钥泄露、严重安全突破 | 立即阻断，任何级别不得验收 |
| P1 | 核心闭环不可用、恢复重复副作用、关键权限失效 | 阻断功能、Milestone 和发布验收 |
| P2 | 功能明显降级但存在安全替代路径 | 不阻断单个内部变更；Milestone 验收需明确批准和计划 |
| P3 | 低影响体验、文案或边缘问题 | 可接受，必须登记 |

规则：

- P0/P1 未解决数量必须为 0；
- 安全相关 P2 默认阻断发布，除非明确接受风险；
- 不得通过降级缺陷级别绕过门槛；
- 已知缺陷必须包含复现步骤、影响、负责人和处理计划。

## 8. Milestone 验收

每个 Milestone 必须：

- [ ] 完成 [MVP-Plan.md](MVP-Plan.md) 对应交付物；
- [ ] 对应验收条目全部通过；
- [ ] 相关测试证据完整；
- [ ] P0/P1 为 0；
- [ ] 未完成项和 P2/P3 已登记；
- [ ] Windows/macOS 差异已验证或明确；
- [ ] 文档、Schema、迁移已同步；
- [ ] 可执行一次该 Milestone 的演示流程；
- [ ] `PROJECT_STATUS.md` 已将该 Milestone 标记为完成。

如果任一必需条目未满足，状态只能是“进行中”“部分完成”或“阻塞”。

## 9. 发布门槛

v0.1 发布必须同时满足：

### 9.1 产品

- [ ] PRD AC-01 至 AC-04 全部通过；
- [ ] 限定场景闭环完成率达到 PRD 目标；
- [ ] 已知限制在产品内明确展示；
- [ ] 最终交付报告可追踪到任务、工具、Artifact 和评价。

### 9.2 工程

- [ ] CI 所有必需门禁通过；
- [ ] Windows 与 macOS 安装、启动、升级、卸载冒烟通过；
- [ ] 数据库迁移、备份和恢复通过；
- [ ] 崩溃恢复不重复副作用；
- [ ] 关键性能目标达到或有批准的偏差记录；
- [ ] 发布包和 Rust Sidecar 完整性可验证。

### 9.3 安全

- [ ] P0/P1 为 0；
- [ ] Key 泄漏测试通过；
- [ ] 路径、符号链接和命令攻击集通过；
- [ ] Electron 安全基线通过；
- [ ] IPC/RPC 越权测试通过；
- [ ] Prompt Injection 不能提升权限；
- [ ] 公开发布前启用签名和 macOS notarization；
- [ ] 依赖、许可证和 Secret 扫描没有未处理高风险项。

### 9.4 质量证据

- [ ] 至少 20 次限定场景 dogfood；
- [ ] 失败已分类；
- [ ] 测试和安全报告对应当前发布版本；
- [ ] 发布报告列出版本、commit、平台、已知缺陷和回滚方案。

## 10. 完成状态用语

Codex 和项目成员只能使用以下状态：

- **完成**：全部适用验收项通过，证据齐全；
- **部分完成**：已有可用成果，但仍有明确未完成验收项；
- **阻塞**：缺少权限、环境、决策或外部条件，无法继续；
- **失败**：实现或验收未达到要求，需要返工；
- **未开始**：尚未进入实施。

禁止用“基本完成”“应该完成”“大概可用”替代明确状态。

## 11. 每次任务的验收报告

最终交付至少包含：

```text
结果：
  完成 / 部分完成 / 阻塞 / 失败

实现内容：
  - ...

需求与设计引用：
  - ...

验证证据：
  - 命令：...
  - 结果：...

未执行验证：
  - 无 / ...

已知问题与风险：
  - 无 / ...

项目状态更新：
  - PROJECT_STATUS.md 已更新
```
