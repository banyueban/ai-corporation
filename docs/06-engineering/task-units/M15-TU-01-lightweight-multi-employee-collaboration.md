# M15-TU-01 轻量多员工文档协作闭环

| 字段 | 内容 |
| --- | --- |
| 任务单元 ID | M15-TU-01 |
| 状态 | 进行中 |
| 所属 Milestone | Milestone 15：轻量多员工协作 |
| 主要结果 | 同一公司中的多名员工可以分别完成资料、内容或检查工作，最终文档只由一名负责人修改和交付，用户能够看清完整分工、交接和最终结果。 |
| 基线提交 | `75397ca` |

## 1. 需求与设计引用

- 用户在 Milestone 14 完成后选择轻量多员工协作为下一方向，并确认“好用第一”；
- 用户于 2026-09-08 确认共享 Workspace、一个文件一个负责人，不开发多人同时修改同一文件、Git worktree、临时分支或自动合并；
- 用户确认 Milestone 15 先验收文档协作，再由 M15-TU-02 验收只有一名编码员工修改代码的编码协作；
- [产品重启说明](../../01-product/Product-Reboot.md#14-轻量多员工协作方向)、[MVP Plan Milestone 15](../MVP-Plan.md#22-milestone-15轻量多员工协作)、[Agent Runtime](../../03-core/Agent-Runtime.md#15-agent-间协作)、[Artifact System](../../03-core/Artifact-System.md)、[UI/UX 文档中心](../../07-ui/README.md)和[简化与后续增强清单 DE-011、DE-023](../Deferred-Enhancements.md#de-011-从单员工扩展到多员工协作)；
- 用户于 2026-09-08 选择 `1A + 2A`：从公司工作区发起协作，由用户选择最终负责人和 Workspace；最终负责人根据当前公司员工的 Skill 自行选择协助员工，分工生成后立即执行，不增加第二次组队确认；协助员工失败不自动重试，最终负责人能继续就使用已有结果继续，不能继续就说明原因并询问用户；取消整项任务会停止所有仍在运行的员工，保留已完成交接和文件作为未完成成果，不自动恢复或重放。

## 2. 前置条件

- Milestone 7–14 已完成，轻量公司、独立员工、单员工任务、模型过程、Skill、环境、Workspace、成果、附件和文档能力可复用；
- 当前分支为 `codex/pi-reboot`，实施基线为 `75397ca`；开始实施时必须记录准确改动并保留其他任务内容；
- 产品、运行、UI、协议和数据设计已按 `1A + 2A` 同步，本合同达到“就绪”；
- Windows 在本机验证，macOS 由同一候选提交的 CI 补充，用户最终使用 Windows 安装包人工验收。

## 3. 包含范围

- 简单任务继续沿用现有单员工入口，不因新增协作能力增加步骤；
- 公司协作从公司工作区单独发起；用户选择最终负责人、共享 Workspace、任务内容和附件；
- 一项文档协作任务至少包含两名同一公司的现有员工，每名员工继续使用自己的 Provider、模型、Skill 和身份；
- 最终负责人看到当前公司其他员工的名称、用途和 Skill，自行决定是否以及怎样委派；分工产生后立即显示并执行，不弹出第二次组队确认；
- 每项分工只有一名员工负责，并明确输入、要交回的结果和当前状态；
- 员工通过应用保存的交接文字、检查意见、附件引用或自己负责的独立文件交付结果；
- 所有员工共享用户为整项任务选择的同一个 Workspace，一个文件始终只有一名明确负责人；
- 最终 Word 或 PDF 只由最终负责人调用现有文档工具生成、修改和核对，其他员工不同时修改该文件；
- 本任务中的协助员工只读取资料并交回文字结果，不获得 Workspace 写入和命令工具；只有最终负责人能够生成或修改最终文件；
- 协助员工失败时不自动重试；最终负责人能继续就明确使用已有结果继续，不能继续就把原因和已有结果展示给用户，由用户选择继续或重新安排；
- 用户取消整项任务时停止所有仍在运行的员工；已完成交接和真实文件保留为“未完成成果”，不自动恢复或重放；
- 用户可看到参与员工、各自模型和 Skill、分工、模型与工具过程、交接结果、最终负责人和整体状态；
- 最终负责人汇总结果并自查后进入用户验收，只有用户确认后整项任务才完成；
- 使用一条真实连续的文档任务验证从发起、分工、交接、最终文档到人工验收的完整流程。

## 4. 非范围

- 不包含编码协作；编码任务由 M15-TU-02 单独实现和验收；
- 不恢复旧 Goal、Plan、DAG、固定 Planner/Executor/Judge 或旧 Corporation 执行入口；
- 不支持多名员工同时修改同一文件，不实现文件锁竞抢、自动合并、Git worktree 或临时分支；
- 不要求每名员工都写 Workspace 文件，调查和检查员工可以只交回应用内记录；
- 不在本任务中增加图片、音频、视频、PPT、表格、OCR、在线市场或新的脚本运行环境；
- 不在本任务中重做正式版 UI；只增加完成本任务所需的清楚界面，正式 UI 由 `DE-022` 的下一独立 Milestone 处理；
- 不提前实现复杂自动组队、员工无限对话、并行调度或专门环境员工。

## 5. 简化与后续增强

- 本任务与 M15-TU-02 共同认领 `DE-011`；两项都通过前不得把多员工协作标记为补齐；
- `DE-023` 记录多人同时修改同一文件、隔离工作区和合并能力，只有真实使用反复需要时才启动；
- `DE-018` 的专门环境员工在多员工基础闭环完成后再单独安排；
- `DE-022` 正式版 UI 设计与重做安排在 Milestone 15 之后，不能用本任务必要界面冒充完成。

## 6. 依赖与接口

- 复用 `pi_company`、`pi_company_employee`、`pi_employee`、`pi_task`、任务事件、附件、工具调用和成果数据；
- 新增的协作记录必须表达整项任务、参与员工、每项分工的唯一负责人、输入、交接结果、最终负责人和真实状态；协议与持久化结构以已同步的 `Task-Protocol.md` 和迁移设计为准；
- 每个文件型分工必须记录唯一文件负责人。写入工具由可信 Main 侧根据当前分工和目标文件判断，模型与 Renderer 不能伪造负责人；
- 非文件交接保存在应用自管数据中，文件交接只保存经过现有 Workspace/成果核对的相对引用，不相信模型声称文件已经生成；
- 员工共享结果不得泄露 API Key、应用私有路径或无关员工的完整上下文，也不得借协作绕过现有工具、环境安装和高风险操作确认；
- 整项状态必须由各分工和最终验收的真实状态计算，任一部分成功不能直接把整体标记完成。

## 7. 交付物与所有权

专属修改区预计包括 M15 文档协作服务、分工与交接记录、文档协作界面、专项 fixture、测试和证据。

共享冲突区包括 Pi Task 协议与 Repository/Service/IPC、公司与员工查询、任务运行、Workspace 文件责任判断、成果、Renderer、UI 文档、迁移、E2E、`PROJECT_STATUS.md` 和 CI。开始实现前必须列出准确文件，并由本任务串行修改。

## 9. 隔离与干扰控制

- 自动测试使用 `M15-TU-01-<random>` 独立 userData、SQLite、公司、员工、Provider fixture、Workspace、任务、交接和成果；
- 每名测试员工使用可区分的固定身份与响应，证明过程和交接没有串错员工；
- 测试至少包含两个员工分别拥有不同结果、最终文件的唯一负责人、协助员工无写入工具和越权写入拒绝；
- 任务取消、应用重启和清理使用独立 fixture，不依赖前一次测试残留；
- M15-TU-01 只关闭文档协作单元，不自动关闭 M15-TU-02、Milestone 15、`DE-018`、`DE-022` 或 `DE-023`。

## 10. 证据计划

- `pnpm check:status`、`pnpm check:task-units`、`git diff --check` 和变更对应的协议、Storage、Desktop、Renderer 测试；
- 多员工身份、模型、Skill、任务归属、唯一文件负责人、交接、Workspace/成果边界、失败、取消和重启专项测试；

## 11. 完成规则

只有 12 项验收断言全部取得当前提交的直接证据、P0/P1 为 0、开发态、最终包、Windows/macOS CI 和用户人工验收全部通过，M15-TU-01 才能标记完成。创建多个任务记录、显示多个员工名字、生成一个文件或其中一名员工成功，都不能单独代替真实文档协作闭环验收；本任务完成也不代表 M15-TU-02 或 Milestone 15 完成。
