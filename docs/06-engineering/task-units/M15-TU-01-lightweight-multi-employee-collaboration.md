# M15-TU-01 轻量多员工协作闭环

| 字段 | 内容 |
| --- | --- |
| 任务单元 ID | M15-TU-01 |
| 状态 | 未开始 |
| 所属 Milestone | Milestone 15：轻量多员工协作 |
| 主要结果 | 复杂任务可由同一公司中的多名独立员工完成清楚的分工、交接和统一交付，简单任务仍可由一名员工直接完成。 |
| 基线提交 | `112980c` |

## 1. 需求与设计引用

- 用户在 Milestone 14 完成后选择下一方向 A：轻量多员工协作；
- 用户同时要求把当前开发验证版界面升级为正式版 UI 的工作加入后续方向；正式 UI 已登记为 `DE-022`，不混入本任务；
- [产品重启说明](../../01-product/Product-Reboot.md#14-轻量多员工协作方向)、[MVP Plan Milestone 15](../MVP-Plan.md#22-milestone-15轻量多员工协作)、[Agent Runtime](../../03-core/Agent-Runtime.md#15-agent-间协作)、[Artifact System](../../03-core/Artifact-System.md)和[简化与后续增强清单 DE-011](../Deferred-Enhancements.md#de-011-从单员工扩展到多员工协作)；
- 当前存在会改变协议、数据、运行、Workspace 写入和 UI 的关键歧义：组队方式、协作写入、最终责任、失败处理和首条验收任务。用户确认前本合同保持“未开始”。

## 2. 前置条件

- Milestone 7–14 已完成，轻量公司、独立员工、单员工任务、模型过程、Skill、环境、Workspace、成果、附件和文档能力可复用；
- 当前分支为 `codex/pi-reboot`，规划基线为 `112980c`；
- M15 的关键产品行为尚未确认，合同未达到“就绪”，不得修改生产协议、Schema、迁移或实现。

## 3. 包含范围

- 简单任务继续使用一名员工，复杂任务允许同一公司中的多名现有员工参与；
- 参与员工保持各自独立的 Provider、模型、Skill 和身份；
- 用户可看到分工、每名员工的过程、交接结果和最终负责人；
- 通过一条真实连续任务验证多员工从开始到统一成果及用户验收的完整流程；
- 具体组队、写入、交接、失败和验收行为在用户决策后补充，届时重新检查合同边界。

## 4. 非范围

- 不恢复旧 Goal、Plan、DAG、固定 Planner/Executor/Judge 或旧 Corporation 执行入口；
- 不在本任务中重做正式版 UI；正式 UI 由 `DE-022` 单独规划；
- 不顺带增加图片、视频、PPT、表格、OCR、在线市场或新的脚本运行环境；
- 不在用户确认前承诺自动组队、并行写入、无限员工对话或自动创建员工。

## 5. 简化与后续增强

- 本任务认领 `DE-011` 的首条轻量多员工协作闭环；复杂自动组队、并行调度和更丰富能力匹配是否继续增强，按本任务真实验收结果另行决定；
- `DE-018` 的专门环境员工必须等多员工交接完成后再单独安排；
- `DE-022` 正式版 UI 设计与重做保持独立，不能用本任务必要的协作界面冒充正式 UI 已完成。

## 6. 依赖与接口

- 预计复用 `pi_company`、`pi_company_employee`、`pi_employee`、`pi_task`、任务事件、附件和成果数据；
- 是否增加父任务/子任务、参与员工、交接记录和最终负责人数据，取决于用户对协作方式的决定；
- 员工共享结果不得泄露 API Key 或应用私有路径，也不得借协作绕过现有工具与安装确认；
- 任何生产接口、状态或迁移必须在合同达到“就绪”后才能确定。

## 7. 交付物与所有权

专属修改区预计包括 M15 协作服务、协作记录、专项测试和证据。

共享冲突区预计包括 Pi Task 协议与 Repository/Service/IPC、公司与员工查询、任务运行、成果、Renderer、UI 文档、迁移、E2E、`PROJECT_STATUS.md` 和 CI；合同就绪后再确认准确文件清单并串行修改。

## 8. 验收合同

- [ ] 01 用户确认组队方式、协作写入、最终责任、失败处理和首条真实验收任务，权威设计与本合同同步更新。
- [ ] 02 简单任务保持现有单员工直接执行，不新增无意义的组队步骤。
- [ ] 03 复杂任务中的参与员工、各自模型与 Skill、分工、过程和交接结果清楚可见。
- [ ] 04 员工只处理明确分配的工作，协作不会绕过 Workspace、工具、环境、秘密和高风险操作边界。
- [ ] 05 多员工失败、取消、重启、退回修改和部分成果显示真实状态，不把部分成功冒充整体完成。
- [ ] 06 最终负责人完成汇总与自查后进入用户验收；只有用户确认后整体任务才完成。
- [ ] 07 一条真实复杂任务在 Windows 开发态和最终包完成多员工分工、交接、统一成果和人工验收。
- [ ] 08 现有单员工、文本、编码、Skill、环境、GIF、附件、Word/PDF 和成果流程回归通过。
- [ ] 09 同一候选提交的 Windows x64、macOS Apple Silicon CI 和用户 Windows 安装包人工验收通过，P0/P1 为 0。

## 9. 隔离与干扰控制

- 自动测试使用 `M15-TU-01-<random>` 独立 userData、SQLite、公司、员工、Provider fixture、Workspace、任务和成果；
- 每名测试员工使用可区分的固定身份与响应，证明过程和交接没有串错员工；
- 并行、重启和清理方式在用户确认协作写入方案后补齐；
- M15 只关闭自身，失败不修改 M7–14 的完成状态，也不把 `DE-018` 或 `DE-022` 自动标记完成。

## 10. 证据计划

- `pnpm check:status`、`pnpm check:task-units`、`git diff --check` 和变更对应的协议、Storage、Desktop、Renderer 测试；
- 多员工身份、模型、Skill、任务归属、交接、Workspace/成果边界、失败、取消和重启测试；
- Windows 开发态、最终打包程序和真实连续多员工窗口旅程；
- 同一候选的 Windows/macOS GitHub Actions 与安装包 artifact；
- 用户对当前 Windows 安装包的人工验收。

## 11. 完成规则

只有用户先确认关键产品行为，合同达到“就绪”后完成实现，并且最终验收合同全部取得当前提交的直接证据、P0/P1 为 0、开发态、最终包、Windows/macOS CI 和用户人工验收全部通过，M15-TU-01 才能标记完成。创建多个任务记录、启动多个模型、显示多个员工名字或其中一名员工成功，都不能单独代替真实协作闭环验收。
