## 1. 为什么重启

旧路线证明了桌面应用、安装包、数据库、工作区、Provider 和 API Key 管理可以运行，但把大量精力花在 Goal、Plan、严格 JSON、状态门禁和层层确认上。真实使用时，用户看不到模型正在做什么，失败后才知道出错；简单任务也被迫经过很重的流程。结果虽然“规则很多”，却不好用。

本次重启不抹掉历史，也不把未通过的 M3-TU-04 说成完成。旧路线停在 Git 标签 `pre-pi-reboot-2026-08-14`。新路线复用已经验收过的工程底座，重新设计真正的产品主流程。

## 2. 产品要做什么

AI Corporation 是一个桌面 AI 公司。用户把任何 AI 能完成的工作交给它，例如：

- 写代码、修改项目、排查问题；
- 处理图片；
- 创作和剪辑视频；
- 编写、整理和修改文档；
- 制作 PPT、表格和其他办公文件；
- 调研、分析、规划，以及未来接入的其他 AI 工作。

软件中的每个“员工”都是一个独立 Agent。每名员工可以独立选择模型、技能和工具，并保留自己的工作上下文。简单任务可以由一名员工完成；复杂任务可以由多名员工分工，但不为了表现“公司”而强行组队。

## 3. 第一原则

**好用是第一原则。**

具体表现为：

1. 用户直接说要做什么并添加附件，不先填写一堆合同和表格；
2. 软件能自己判断的事情就自己做，只有确实缺少关键信息时才提问；
3. 用户选定的任务范围内，员工可以自动读取、写入和使用工具；
4. 删除重要内容、产生费用、对外发布或给别人发送消息等高风险动作，必须先让用户确认；
5. 员工完成后先自查和修改，认为可交付时进入“等待用户验收”；只有用户确认后才算完成；
6. 约束只保留能防止真实损失、泄密和误操作的部分，不让内部规则妨碍普通工作。

## 4. 用户必须看得到过程

默认界面显示简洁进度，但用户可以随时展开查看：

- 软件实际发给模型的完整内容；
- 模型正在返回和已经返回的原始内容；
- 员工准备调用、正在调用和已经调用的工具；
- 工具输入、结果、耗时和错误；
- 当前正在做什么、为什么失败、下一步准备做什么。

只有 API Key、Authorization 等认证秘密必须隐藏。不得因为“日志安全”而把普通模型输入、模型输出或工具过程全部藏起来。

## 5. 使用 Pi 的结论

新路线采用 `@earendil-works/pi-ai` 和 `@earendil-works/pi-agent-core` 作为员工运行基座：

- `pi-ai` 负责模型接入、流式输出和工具调用；
- `pi-agent-core` 负责一名员工的运行循环、上下文和事件；
- 编码员工后续可按需复用 `pi-coding-agent`，但它不作为整个产品的强制核心；
- `pi-telemetry` 只在确有需要时用于内部耗时和错误统计；
- `pi-tui` 不用于桌面界面，继续使用现有 Electron + React。

用户已经实际确认 Pi 可以使用现有 DeepSeek 模型。AI Corporation 负责 Pi 没有提供的产品能力：员工管理、每名员工的模型和技能设置、团队分工、桌面交互、持久化、任务历史、权限确认和最终验收。

## 6. 复用和停止的内容

继续复用：

- Electron + React 桌面壳和 Windows/macOS 打包；
- SQLite、迁移和本地数据基础；
- 工作区选择与边界；
- AI Corporation 自己保存和管理 API Key 的能力；
- Provider 配置和连接验证；
- CI、自动测试和真实窗口验收经验。

停止作为新主流程：

- 先生成 Goal Contract 再生成 Plan 的强制入口；
- 所有模型结果都必须塞进复杂严格 JSON 的做法；
- 简单任务也必须建立固定 Planner、Executor、Judge 团队；
- 用户看不到实时模型调用，只能等待成功、超时或报错；
- 还没有真正产出工作成果时，用大量内部状态冒充进展。

旧数据和旧代码先保留，不在重启过程中偷偷删除。旧 Goal/Plan 公司不再进入新产品主流程，也不在设置中提供查看入口。

## 7. 重启后的第一个可用闭环

第一步只验证一名 Pi 员工，不立即做多员工公司：

```text
创建员工
→ 为员工选择一个真实模型和一项或多项技能
→ 输入一个真实任务
→ 实时看到模型输出和工具过程
→ 员工交付结果或清楚说明阻断
→ 用户确认是否通过
```

这个闭环必须在 AI Corporation Desktop 的真实窗口中完成，并最终提供 Windows 安装包人工验收。它通过后，才继续做附件、通用工具、更多任务类型和多员工协作。

## 8. 首阶段不做什么

- 不立即恢复旧的 Goal、Plan、DAG 和固定三角色流程；
- 不立即做多员工自动组队；
- 不一次接入图片、视频、文档、PPT 的全部专用工具；
- 不因为未来可能需要而先造大型通用协议；
- 不把单元测试、构建成功或进程存活当作桌面软件可用。

这些边界是为了先证明产品真的好用，不代表产品永远不需要相邻能力。未来能力必须在有真实使用需求时建立独立任务并单独验收。

## 9. Pi 路线的轻量公司

Milestone 7–9 已证明一名 Pi 员工可以完成真实文本和编码任务。接下来“公司”不再表示一次 Goal/Plan 执行，而是用户长期使用的简单工作空间：

- 公司保存名称、成员员工、常用工作区和任务历史；
- 员工仍是独立 Agent，模型和多项 Skill 配置只保存一份，可以加入多家公司；
- 工作区可以被多家公司复用，每次任务仍明确选择实际工作区；
- 每项任务只属于发起它的一家公司，任务过程、结果和验收不能串到其他公司；
- 创建公司只填写名称，不强制目标合同、规划、预算或组队；
- 旧 `Corporation → Goal → Plan → Organization → Agent Run` 数据原表保留，不迁移成新公司，也不在控制台或设置中提供入口。

升级已有 Pi 数据时，软件自动创建可改名的“我的公司”，把现有 Pi 员工、任务和任务使用过的工作区接入该公司。迁移不得改写任务内容、过程、状态或验收结果，也不得重新调用模型、工具或命令。

## 10. 标准 Agent Skills 路线

员工能力使用开放的标准 Agent Skills 文件夹，不为每类工作重复发明私有能力格式。一名员工可以分配多项 Skill；任务开始时只向模型提供这些 Skill 的名称和用途，员工按任务自动启用匹配 Skill，再按需读取完整说明、参考资料、脚本和资源。

Skill 继续由用户明确导入并由 AI Corporation 保存独立副本。Skill 自带的 `allowed-tools`、脚本或文字不能自行获得工具权限。JavaScript 使用软件自身运行能力；Python 缺失时由软件安装到自管目录；Windows 支持 PowerShell，macOS 支持 Shell，其他脚本类型明确说明暂不支持。

软件自动识别 PEP 723、`requirements.txt` 和 `package.json` 中的依赖。Skill 只在文字中说明依赖时，员工可以提交包名和版本组成的结构化列表，不能提交任意安装命令。默认给每项 Skill 建立可跨任务和公司复用的独立环境；Skill 明确要求项目环境时才写入当前 Workspace。Skill 或依赖变化后必须重新检查。

缺少运行环境时，软件必须说明缺什么并提供“自动安装”或“暂不安装”。独立环境安装需要单独批准；系统级安装只允许受限 winget 或 Homebrew 方案，并再次展示精确命令和影响。安装后必须复检通过再继续任务。当前由环境管理工具处理，未来可以增加专门环境员工复用该工具，但不能绕过同一审批边界。

## 11. 首个真实公开 Skill

Milestone 13 固定使用 Anthropic `skills` 仓库提交 `3b3fad96af16a10759d930941b4520ba0c40edae` 中未经修改的 `slack-gif-creator`，许可证为 Apache 2.0。它必须按原目录导入、分配给员工并由员工按任务自动启用，不能为了适配 AI Corporation 修改公开 Skill 的说明、依赖或代码。

该 Skill 本身没有可直接运行的 `scripts/`，而是提供 `core/` Python 工具。因此，员工会在当前 Workspace 写入一份普通 Python 脚本；软件使用该 Skill 的独立环境运行脚本，并让脚本只读使用 Skill 自带的 `core/`。工作区脚本、Skill 内容和真实成果都必须重新核对，模型与界面不得看到应用自管 Skill 或环境的绝对路径。

首次运行时，软件识别公开 `requirements.txt` 中的 Pillow、imageio、imageio-ffmpeg 和 numpy，展示安装计划并经用户批准后安装到可复用的 Skill 独立环境。环境就绪后仍需单独批准本任务运行脚本。生成的动画 GIF 经真实文件和 Skill validator 核对后进入成果区，并可在软件内播放预览、用系统打开或查看所在位置。

这一阶段只证明首个真实公开 Python Skill 的完整流程。它不交付附件入口、通用图片编辑、视频、Office、在线市场或任意公开 Skill 兼容；这些能力继续按真实需求另建任务。

## 12. 任务附件与首个文档闭环

Milestone 14 让用户直接给员工添加真实文件，不要求先把文件复制到 Workspace。用户选择或拖入 `.docx`、`.pdf`、`.txt`、`.md` 后，AI Corporation 为当前任务保存一份应用自管副本，原文件不修改；界面、模型和 Skill 只看到附件名称、类型、大小和任务内 ID，不看到原始绝对路径或应用私有路径。

首版内置一个由 AI Corporation 独立编写、符合标准 Agent Skills 格式的“文档处理”Skill。Skill 通过通用的 `document_read` 和 `document_create` 工具读取附件、生成新的 Word 或 PDF；处理步骤保留在 Skill 中，工具不写死具体写作任务。其他符合标准的 Skill 以后可以复用同一工具。

首版支持 Word、文本、Markdown 和带文字层的普通 PDF。Word 修改保留标题、段落、列表和表格等常用逻辑结构，但不承诺复杂页眉、目录、文本框、修订或像素级排版完全不变；扫描 PDF 没有可提取文字时明确说明暂不支持文字识别。所有处理结果写成 Workspace 中的新文件，不覆盖附件原件或已有文件。
