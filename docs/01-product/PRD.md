# AI Corporation Desktop v0.1 产品需求文档

| 属性 | 内容 |
|---|---|
| 文档版本 | 1.0 |
| 产品版本 | v0.1 MVP |
| 状态 | Development Ready |
| 产品形态 | Windows / macOS 桌面应用 |
| 核心定位 | 受控自主任务执行系统 |

## 1. 产品摘要

AI Corporation Desktop 让用户以“目标”而非连续 Prompt 驱动 AI。系统在本地工作区内自动完成目标澄清、任务规划、临时团队组建、执行、验收、修订和交付。

“Corporation”是一种内部组织模型，不是拟人化公司模拟器。对用户而言，它是一套可观察、可暂停、可审批、可恢复的自主任务执行工具。

## 2. 问题陈述

现有聊天式 AI 要求用户承担大量管理工作：

- 把复杂目标拆成步骤；
- 为每一步选择模型或工具；
- 保存上下文和中间产物；
- 判断回答是否正确；
- 在失败后决定如何重试；
- 控制费用与危险操作。

v0.1 要验证：系统能否在明确边界内接管这些管理工作，并比单轮聊天更稳定地交付结果。

## 3. 目标与非目标

### 3.1 产品目标

| ID | 目标 | 成功信号 |
|---|---|---|
| G-01 | 目标驱动 | 用户只需描述目标、约束与期望交付物 |
| G-02 | 自动规划 | 系统生成可编辑、带依赖和验收标准的任务图 |
| G-03 | 动态组队 | 系统为任务创建 Planner、Executor、Judge 等最小角色集 |
| G-04 | 受控执行 | 在预算、权限和工作区边界内调用模型与工具 |
| G-05 | 独立验收 | 关键产物经过确定性检查和/或独立 Judge |
| G-06 | 可观察可恢复 | 用户可查看、暂停、审批、重试；应用重启后继续 |
| G-07 | 模型可替换 | 不把任务定义或 Agent 定义绑定到单一厂商 |

### 3.2 v0.1 非目标

- 不承诺完成任意开放世界任务；
- 不实现真正无人监管的系统级操作；
- 不实现 Agent 市场、经济系统、晋升或自动淘汰；
- 不实现多用户、云同步、团队协作或企业管理后台；
- 不实现 Agent 自我复制、自改权限、自改核心制度；
- 不训练模型，不内置重量级本地推理运行时；
- 不把浏览器自动化、生产发布、付款、发信作为默认能力；
- 不实现通用 DAG 可视化编辑器，只提供计划审阅和有限编辑；
- 不把 LLM 自评分数当作客观正确率。

## 4. 目标用户与首个使用场景

### 4.1 主要用户

熟悉 AI 工具、希望让 AI 连续完成多步知识工作的个人开发者、产品经理、研究人员和内容工作者。

### 4.2 v0.1 推荐任务

- 在指定工作区生成一组结构化产品或技术文档；
- 分析本地资料并输出报告；
- 对小型代码仓库进行只读分析；
- 在用户授权后创建或修改项目内文件；
- 对产物执行 Schema、链接、格式、测试或独立审阅。

### 4.3 不推荐任务

- 无法定义成功标准的开放式长期经营；
- 涉及支付、生产发布、外部消息发送的任务；
- 医疗、法律、投资等高风险决策；
- 需要绕过系统权限或访问未授权目录的任务。

## 5. 核心用户旅程

### 5.1 首次设置

1. 用户启动应用；
2. 选择一个模型提供商并录入凭据；
3. AI Corporation Desktop 将凭据保存到应用自管 Key Vault；
4. 执行最小连接测试；
5. 用户设置默认模型、预算和审批偏好。

验收标准：

- 凭据不以明文写入 SQLite 或日志；
- 测试失败时显示可行动的错误信息；
- 至少支持一个可用 Provider Adapter。

### 5.2 创建 Corporation

1. 用户选择本地工作区；
2. 输入名称、目标、约束、期望交付物；
3. 用户明确选择已验证的 Provider/精确模型，系统生成 Goal Contract；
4. 若存在影响方案的关键缺口，系统按每周期最多 5 轮进行结构化澄清；达到周期上限时停止模型调用，由用户决定开启下一个 5 轮周期、保存含未确认 HIGH 假设的草稿或取消；
5. 用户确认合同后才可进入规划。

验收标准：

- 用户可编辑 Goal Contract；
- 系统明确显示范围、假设、成功标准和预算；
- 未确认的高影响假设不能被静默当作事实。
- Goal 分析前明确显示接收数据的 Provider 与精确模型；Workspace 路径和文件内容不发送给 Provider。

### 5.3 规划与组队

1. Planner 生成 Task Graph；
2. 系统验证图无环、输入输出闭合、每项任务可验收；
3. 系统展示每个 Task 的能力要求和建议角色，并明确标注尚未组队；真实 Organization Engine 在 Milestone 3 创建最小 Agent 集；
4. 用户可审阅计划并开始执行。

验收标准：

- 每个叶子 Task 都有预期输出和验收标准；
- Task Graph 是 DAG；
- v0.1 默认并发上限为 2；
- 计划修改产生新版本并保留旧版本。

### 5.4 执行、审批与恢复

1. Scheduler 将 Ready Task 分配给 Agent；
2. Agent 调用模型并按需请求工具；
3. Policy Engine 判定允许、拒绝或请求审批；
4. 中间状态和事件持续写入 SQLite；
5. 应用退出后，未完成 Run 标记为可恢复；
6. 重启时从最后安全检查点恢复，而非重复已提交副作用。

### 5.5 验收与交付

1. 先运行确定性验证；
2. 需要语义判断时调用独立 Judge；
3. 未通过则根据问题类型修订、重规划或请求用户；
4. 通过后生成最终交付摘要；
5. 用户可打开产物、查看证据与导出运行报告。

## 6. 功能需求

### FR-001 工作区管理

- 选择并授权一个本地根目录；
- 显示用户主动授权的路径和真实读写权限；
- 默认禁止访问根目录之外；
- 工作区不存在或权限变化时进入 `WAITING_HUMAN`。

Renderer 只能获得用于展示的授权路径、Workspace ID 和权限状态；规范化绝对路径及路径边界判断只存在于 Electron Main 与 Rust 可信边界中。

### FR-002 Provider 与模型配置

- 新增、编辑、测试、禁用 Provider；
- 配置 Endpoint、模型、超时、最大输出和价格元数据；
- API Key 由 AI Corporation Desktop 的应用自管 Key Vault 存储和管理；
- Provider 配置与 Key Vault 记录分离；
- Provider 编辑页默认遮挡已存 Key，用户主动选择查看时可以读取明文；
- 允许为 Planner、Executor、Judge 指定不同模型策略。

### FR-003 Corporation 管理

- 创建、查看、暂停、恢复、取消、归档；
- 显示目标、进度、预算消耗和当前阻塞；
- 删除属于破坏性动作，必须二次确认；
- v0.1 不提供跨设备同步。

### FR-004 Goal Contract

- 从用户输入生成结构化合同；
- 支持编辑、确认和版本化；
- 字段包含成功标准、交付物、约束、假设、非目标；
- 合同变更触发计划影响分析。
- 模型生成只要求名称、已授权 Workspace 和目标；成功标准、交付物、约束与非目标是可选提示；
- 每个生成阶段的非法 JSON 最多修复一次；每个澄清周期最多 5 轮，续期必须由用户明确确认；
- 达到周期上限后，用户可继续下一周期、保存带未确认 HIGH 假设的草稿或取消；保存草稿不代表批准、规划或执行。

### FR-005 Task Graph

- 生成 Task、依赖边和里程碑；
- 显示列表与依赖关系；
- 支持修改标题、说明、验收标准、依赖与优先级；
- 支持暂停、取消、重试单个任务；
- 检测循环依赖、孤立任务和未定义输出。

### FR-006 Organization 与 Agent

- 自动生成最小角色集；
- 展示角色、能力、模型策略、工具和权限；
- 支持 Planner、Executor、Judge；
- 同一关键产物的 Executor 与唯一 Judge 不得相同；
- Agent Definition 可复用，Agent Run 必须隔离。

### FR-007 执行引擎

- 支持结构化模型输出；
- 支持有限工具调用循环；
- 每次 Run 有最大轮数、Token、成本和时限；
- 支持取消信号；
- 对瞬时错误退避重试，对确定性错误不盲目重试。

### FR-008 工具与审批

v0.1 内置工具：

- 目录列举；
- 文本文件读取；
- 文件搜索；
- 在工作区内创建/修改文件；
- 受限命令执行；
- 运行预配置测试命令。

策略结果：

- `ALLOW`
- `DENY`
- `REQUIRE_APPROVAL`

审批界面必须展示：

- 谁请求；
- 要执行什么；
- 精确目标；
- 风险；
- 预计副作用；
- 仅本次允许或记住该规则。

### FR-009 Artifact

- 文本、JSON、文件、补丁、报告均作为 Artifact 登记；
- 保留版本、哈希、创建者、来源与状态；
- 大文件存文件系统，数据库保存元数据和相对路径；
- 用户可从最终交付追溯到输入与验证证据。

### FR-010 Evaluation

- 支持规则、Schema、文件、测试命令、LLM Judge；
- 每项成功标准至少对应一个检查；
- 输出 `PASS`、`FAIL`、`NEEDS_HUMAN`；
- 失败包含可操作问题，不只给分；
- 最多自动修订 2 次，之后请求用户或失败。

### FR-011 运行时间线

- 展示状态变化、模型调用、工具请求、审批、Artifact 和评价；
- 默认隐藏敏感 Prompt/响应细节，允许用户展开脱敏内容；
- 事件可按任务和 Agent 筛选；
- 错误信息包含恢复建议。

### FR-012 预算与停止条件

- Corporation 级 Token、成本、时间预算；
- Task 可获得子预算；
- 达到 80% 时提示，达到 100% 时停止新调用；
- 用户可明确增加预算；
- 取消后不得启动新的模型或工具调用。

### FR-013 持久化与恢复

- 状态变化与副作用前后建立检查点；
- 重启后列出可恢复 Corporation；
- 对不确定是否完成的外部副作用不得自动重放；
- 恢复操作保留审计事件。

### FR-014 最终交付

- 显示目标完成情况；
- 列出交付物、未满足条件、已知限制、成本和耗时；
- 支持打开文件所在位置；
- 支持导出 Markdown 运行报告。

### 7.1 页面

Onboarding
Dashboard

└── Settings
Global Settings

### 7.2 Corporation Workspace 布局

- 顶部：状态、暂停/恢复、预算、当前阻塞；
- 左侧：任务与里程碑；
- 中央：当前任务、产物和计划；
- 右侧：团队、审批与关键事件；
- 底部抽屉：详细日志与模型/工具调用证据。

v0.1 不追求“公司办公室”视觉拟人化，优先清晰呈现执行状态和控制权。

页面信息层级、核心流程、低保真线框、交互状态和 UI 专项验收以 [UI/UX 文档中心](../07-ui/README.md)为实现基线。UI 设计不能扩张本 PRD 的功能范围。

## 8. 状态与异常体验

| 情况 | 系统行为 |
|---|---|
| 模型限流 | 指数退避并显示等待状态 |
| Provider 不可用 | 使用用户允许的回退模型，否则暂停 |
| 输出不符合 Schema | 同一 Run 进行一次修复，再失败则重试或升级 |
| 工具被拒绝 | 不绕过；重新规划或请求用户 |
| 预算耗尽 | 暂停新调用，生成当前进展摘要 |
| Judge 连续失败 | 最多修订两次，然后请求用户 |
| 应用崩溃 | 从持久化检查点恢复 |
| 工作区文件被外部修改 | 检测哈希冲突，禁止静默覆盖 |

## 9. 非功能需求

### 9.1 跨平台

- Windows 10/11 x64；
- macOS 13+，Apple Silicon 为首要目标，Intel 视构建资源支持；
- 业务代码共享，不维护平台专属功能分支，平台差异封装在适配层。

### 9.2 性能

- 冷启动目标：主流设备 ≤ 5 秒；
- 普通页面交互 P95 ≤ 150ms；
- 10,000 条事件时间线虚拟滚动可用；
- SQLite 查询不得阻塞渲染线程；
- 空闲时 CPU 占用接近 0，不持续轮询。

### 9.3 可靠性

- 所有核心状态事务性持久化；
- 单次 Provider 故障不损坏项目状态；
- 不重复提交已确认的文件写入；
- 可取消操作在 2 秒内进入取消流程，外部调用按能力终止。

### 9.4 安全与隐私

- Electron 启用 `contextIsolation`，禁用 renderer 的 Node 权限；
- IPC 采用白名单和 Schema 验证；
- API Key 使用 AI Corporation Desktop 自管的本地 Key Vault：完整 Key 仅以密文进入 SQLite；应用自行生成并在应用数据目录保存本地加密密钥，不使用 OS Keychain、Credential Manager 或 Native Core 作为存储；
- 该静态保护只避免 SQLite 数据库被单独读取时直接暴露 Key；同时取得数据库与应用本地加密密钥的攻击者仍可解密，产品不得把它描述为系统级强机密保护；
- 日志默认脱敏；
- 文件与命令限制在工作区和策略允许范围内；
- Prompt 注入内容不得提升工具权限。

### 9.5 可维护性

- 核心协议使用版本字段；
- Provider、Tool、Evaluator 采用稳定接口；
- 数据库迁移可向前执行并可备份；
- 关键状态机和策略必须有单元测试。

## 10. 产品级验收场景

### AC-01 文档任务闭环

给定目标“在空工作区创建一套结构化项目文档”，系统应：

1. 创建 Goal Contract；
2. 生成至少三个有依赖的 Task；
3. 创建 Planner、Writer/Executor、Judge；
4. 经用户批准后写入多个 Markdown 文件；
5. 验证文件存在、内部链接有效、章节满足要求；
6. 交付报告显示全部证据。

### AC-02 权限阻断

当 Agent 尝试访问工作区外文件时：

- Policy Engine 拒绝或请求明确扩权；
- Agent 无法通过 Prompt 或改写路径绕过；
- 时间线记录判定原因。

### AC-03 恢复

执行过程中强制关闭应用并重启：

- Corporation 恢复为 `PAUSED` 或可安全继续状态；
- 已写入并提交的 Artifact 不重复生成副作用；
- 用户可继续剩余 Task。

### AC-04 质量修订

当首次 Artifact 缺少必需章节时：

- Evaluation 返回结构化问题；
- Executor 基于问题生成新版本；
- 旧版本仍可追溯；
- 第二次通过后交付。

## 11. 产品指标

v0.1 内测阶段以离线/本地聚合为主，不默认上传遥测。

| 指标 | 定义 | 初期目标 |
|---|---|---|
| 闭环完成率 | 无人工代做且产物通过验收的 Corporation 占比 | ≥ 60%（限定场景） |
| 可恢复率 | 异常退出后可继续的活跃 Corporation 占比 | ≥ 95% |
| 权限违规数 | 未审批的越界副作用 | 0 |
| 首次计划可接受率 | 用户无需结构性重写即可启动的计划占比 | ≥ 70% |
| 平均修订次数 | 每个通过任务的自动修订次数 | ≤ 1.5 |
| 预算超支率 | 超过硬预算的运行占比 | 0 |

## 12. 发布门槛

- 四个产品级验收场景全部通过；
- Windows 与 macOS 安装、升级、卸载冒烟测试通过；
- 高风险安全用例无 P0/P1 缺陷；
- 数据库迁移、崩溃恢复和凭据存储验证通过；
- 至少完成 20 次限定场景 dogfood，记录失败分类；
- 已知限制在产品内清晰展示。
